# T100 Persistent sessions and a scoreboard

- **Kind**: feature (0.2.1)
- **Issue**: #254 · **Branch**: the session branch · **Merge after**: T98
- **Review**: none per PR; the 0.2.1 milestone review (#253) covers it, on the moved candidate.
- **Evidence**: owner decisions, 2026-10-22 (in this session): the same browser is enough; totals and recent games; in 0.2.1. [designed] throughout.
- **Owns**: `src/ui/geographicGame.ts`, `src/ui/referenceBattleGame.ts`, `src/ui/battleChrome.ts`, `src/ui/victoryView.ts`, `src/ui/help.ts`, a new `src/ui/scoreboard.ts`, `src/styles.css`, `docs/play.md`, `tools/release/PLAY.md`, `docs/releases/0.2.1/ACCEPTANCE.md` (a line for this task), `tests/e2e/persistence.spec.ts`, `tests/e2e/scoreboard.spec.ts`, `tests/ui/scoreboard.test.ts`, and the existing specs the change makes wrong.
- **Scope**:
  - **Sessions persist in this browser** over a reload or a browser restart (T96 already keeps the root game; this hardens it):
    - a `?seed=N` game keeps its own record, per seed, resumed by the same URL; it still never replaces the root game's record;
    - game speed and Pause survive a reload (a game paused before the reload opens paused);
    - a choice in progress (capture, card choice, Raid) reopens on resume, as the engine state already holds it.
    - Never a server, account or cross-device sync.
  - **A scoreboard**, kept in this browser (`localStorage`), behind a trophy icon in the menu:
    - totals: played, won, lost, given up, and the win rate;
    - the last 20 games, newest first: date, result (Won, Lost, Gave up), rounds, your countries at the end, and the seed;
    - **Reset** asks "Clear the scoreboard?" before clearing.
  - **What counts:** each player game (the root page and `?seed`; never `?setup`, `control=manual` or Nine Isles) is recorded exactly once, when it ends: a win, an elimination (Lost, at once, even if the player then watches the computers), or New game's give-up. A reload of a finished or recorded game never records it again.
  - The result card shows the updated totals line (for example "Won 3 · Lost 2 · Gave up 1").
  - A corrupt scoreboard record starts an empty one without an error.
- **Done when**:
  1. `npx playwright test tests/e2e/persistence.spec.ts tests/e2e/scoreboard.spec.ts --workers=2`. It must show:
     - a `?seed=7` game resumes after a reload with the same history and RNG, and the root game's record is untouched;
     - a game left paused opens paused after a reload, and a changed speed survives a reload;
     - a pending capture survives a reload (its card is open, the engine state is the same);
     - a reload in a new page of the same browser context (a "restart") resumes the root game;
     - a give-up adds exactly one "Gave up" row and the totals change by one; a reload does not add another;
     - a win and an elimination each add exactly one row, Won and Lost, using fixtures or the engine to reach the end;
     - a 21st game drops the oldest row;
     - Reset asks first, and clearing empties the totals and the list;
     - a corrupt scoreboard starts empty without a page error;
     - a `?setup` game never adds a row.
  2. `tests/ui/scoreboard.test.ts` covers recording, the 20-row cap, the totals and win rate, and dedupe by game id.
  3. `npm test && npm run build` pass; existing specs still pass without weakening an assertion.
- **Hazards**:
  - **Record once.** Give every player game an id stored with its record, and keep the recorded ids, so render loops and reloads never double-count.
  - **The record is the versioned save text.** Never store a raw state; replay checks apply on resume. Preferences are separate keys.
  - **Tests start clean.** Each Playwright test has a fresh browser context, so nothing leaks between tests; keep it so.
